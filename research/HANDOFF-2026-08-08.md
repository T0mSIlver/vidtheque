# vidtheque — design handoff (2026-08-08)

Decisions from the design conversation (website-repo session). Read this first when picking up in the cloned `vidtheque` repo; move this file + the two research docs into `research/` there.

## What it is

**vidtheque**: a self-hostable **remote** MCP server maintaining a *persistent, cross-video, multimodal corpus* of videos — "a searchable memory of everything you've watched." Transcript + on-screen text (OCR) + frame embeddings, cross-video search with timestamped citations (`https://youtu.be/ID?t=123` deep links). The landscape survey (see `landscape-survey-video-mcp.md`) validated the gap: nobody combines (1) persistent multimodal index behind MCP, (2) visual embeddings in an MCP server, (3) fully local GPU / no third-party API, (4) remote OAuth deployment.

Name checked clean 2026-08-08: npm free, PyPI free, `vidtheque.dev` unregistered, zero exact-name GitHub repos, 1 name-mention. Runner-up was `vidarium`. License suggestion: MIT.

## Architecture

**Monorepo**, two Docker images from one repo:

```
vidtheque/
├── mcp/       # CPU MCP server: OAuth (MCP spec, dynamic client registration — claude.ai compat), yt-dlp,
│              # SQLite + sqlite-vec index, keyframe JPEGs, job queue, pipeline orchestration
├── worker/    # custom GPU inference worker (Tom owns model serving deliberately — inference is his lane)
├── deploy/    # docker-compose.yml (profiles: gpu, tunnel), .env.example, cloudflared notes
├── bench/     # benchmark scenarios + results (blog fuel)
└── .github/workflows/  # path-filtered GHCR builds; mcp image multi-arch (runs on a Pi)
```

- Boundary: worker is a **stateless inference API**, OpenAI-compatible (`/v1/audio/transcriptions`, `/v1/embeddings`, custom `/v1/ocr`). HTTP only between mcp/ and worker/ — no Python imports across, even in tests. OpenAPI file in worker/ is the contract. No-GPU self-hosters point `WORKER_URL` at hosted providers instead.
- Worker internals: per-task backend abstraction (`STTBackend`/`EmbedBackend`/`OCRBackend`, env-selected — the experimentation surface), one lifecycle manager owning the GPU (job queue serializing GPU work, load-on-demand, idle-TTL unload, NVML VRAM accounting), `GPU_ACQUIRE_CMD`/`GPU_RELEASE_CMD` hooks (Tom's llama.cpp lease lives outside the shared code). Env var decides whether the embedding model stays resident (~1–2GB) or unloads.
- Deterministic builds: uv lockfile, digest-pinned CUDA base image, versions as build args, GHCR publish on tag. CI on CPU paths (ctranslate2/ONNX); GPU validation = `make bench` on the box. No self-hosted runner on the public repo (security).

## Tom's box specifics (not for the public repo)

Proxmox host, RTX 3090 (24GB), llama.cpp LXC in router mode. Key facts: LXC GPU sharing is bind-mounted device nodes — **multiple LXCs can share the GPU** (only VM/VFIO is exclusive); recommended: run the worker beside llama-server in the same LXC. Lease: NVML free-VRAM check first (whisper+embed+OCR peak ~3–4GB loaded sequentially — often no eviction needed); evict via router unload endpoint or `systemctl stop llama-server` (bulletproof; race-free). Query-time tools touch only SQLite/JPEGs — GPU dance is indexing-only. Public exposure: cloudflared tunnel → `vidtheque.tomvaucourt.com`-style hostname; OAuth in the MCP server itself (NOT Cloudflare Access — self-hosters don't have his Access setup; he wants claude.ai-client compat from day one).

## Model/tooling picks (from the survey — receipts in the research docs)

- STT: **whisperX** (word-level forced alignment → precise deep links; faster-whisper itself is in maintenance).
- Frame embeddings: **SigLIP 2 NaFlex** (best open model on text-in-image/OCR-ish retrieval; preserves aspect ratio — slides/terminals).
- OCR: **RapidOCR** (ONNX, easy to containerize) or PaddleOCR. Never Tesseract.
- Keyframes: **PySceneDetect** shot detection + perceptual-hash dedup + **Laplacian-variance sharpness filter** (scene-cut frames are blurry; pick sharpest per shot). TransNetV2 only if gradual transitions matter.
- Index: SQLite + **sqlite-vec** (alpha caveat — brute-force KNN; SQLite's Vec1 is the escape hatch). FTS5 **external-content** tables (screenpipe receipt: 420× faster deletes).
- VLM: **dropped for now** — the client model is the VLM. Local VLM captions = optional later pass.
- Text embeddings: same model at index and query time, pinned in one shared config value.

## Tool surface direction (~8–10 tools; full rationale in `screenpipe-tool-surface-deep-dive.md`)

- One `search` tool with `content_type: all|transcript|ocr|frame` (all must MEAN all). **Two time axes**: `published_after/before` (corpus) vs `offset_start/end` seconds (intra-video). Case-insensitive `channel`/`video_title` filters. Relevance-primary ordering (`order=relevance|recency|video_time` explicit — never recency-only). Per-video diversity cap (ROW_NUMBER ≤ N). Adjacent-cue clustering into `{video_id, start, end, text, cue_ids[]}`. OCR-vs-transcript dedup (keep longer text). FTS candidate cap (`ORDER BY rank LIMIT 5000`) as the seam where embedding rerank slots in.
- `video-summary` + `corpus-summary` rollups with `include_*` toggles, `max_*` caps, `data_status` self-diagnosis, `guidance.next_best_query`.
- `get_frames` with `return: "image"|"url"` — **URL default** (authenticated `/frames/<id>.jpg`): Claude Code mangles MCP ImageContent into raw base64 text (issue #31208, closed not-planned; 10–20× token blowup). Nobody else ships the URL variant — publishable contribution.
- `get-segment-context` (transcript window around t + nearby OCR + chapter), `index_video` (async → job id) + `job_status`, maybe `get-clip`.
- MCP **resources**: corpus listing (browse before search), a `context` resource with precomputed timestamps, a progressive-disclosure `guide` (summary → search → drill-down-by-id; USE WHEN / DO NOT USE in every description).
- Token discipline (screenpipe receipts): middle-truncation default 1000 chars with documented `0` opt-out; pagination hints printed in payloads (`use offset=N for more`); `has_more` via LIMIT n+1, never exact totals from a duplicated count query; every list tool double-capped (items AND chars); expensive paths bounded independently of `limit`; columnar `format=tsv` + `fields=` for list outputs (−73%).
- Ops contract: 408 "narrow your range" + 503 + Retry-After + real query cancellation (SQLite progress handler) — all three together; byte-weighted response cache with long TTL (corpus is static until reindex).
- MCP tool annotations (readOnlyHint/idempotentHint) on every read tool.

## Corpus product ideas (the differentiator)

Channel/playlist subscriptions (cron auto-index of new uploads); "send to index" bookmarklet as watch-later replacement; collections/tags (namespaced: `topic:`, `person:`) scoping search + `include_related` co-occurrence; markdown export per video (Obsidian-friendly, data never hostage); later: any yt-dlp site / local files — the corpus framing makes that coherent.
