# vidtheque — first end-to-end CPU smoke (2026-08-08)

First real run of the whole loop: `index-video` → pipeline → `search` and the
rest of the tool surface, over the real MCP streamable-HTTP transport, against
a real YouTube video, **on CPU only** (no GPU on this box at all — NVML is not
even installed, and the worker says so at boot).

Harness: `scripts/e2e_smoke.py` (new, this session). It is **not** part of
`make test` and must not become part of it: it downloads ~5.5 GB of model
weights and hits YouTube. `make test` stays CPU-only, offline and
download-free.

**Verdict: the loop is real.** One command, one URL, 2 min 20 s later a
2:29 screencast is searchable by what was said, by what was on screen, and by
what the frames *look like* — all three legs returning correct timestamped
deep links, from an index built by the real pipeline through the real tool
surface. Six defects found, none fatal; two of them (§4.1, §4.2) are the kind
that would make a first-time operator conclude the product is broken.

---

## 1. What ran

| Piece | How |
|---|---|
| worker | `python -m vidtheque_worker`, `DEVICE=cpu`, CPU torch wheels, **no whisperX** |
| mcp | `python -m vidtheque_mcp`, `VIDTHEQUE_AUTH=none`, `127.0.0.1:8390`, fresh data dir |
| client | the `mcp` package's own `Client` over streamable HTTP (`http://127.0.0.1:8390/mcp`) |
| video | `https://youtu.be/5C_HPTJg5ek` — Fireship, "Rust in 100 Seconds", 2:29 |

**Why that video.** 149 s (inside the 2-6 min budget), 5 chapters, a heatmap,
English auto-captions in word-timed `json3`, and it is wall-to-wall on-screen
text — editor panes, a terminal with `rustc` errors, crates.io, `Cargo.toml` —
which is exactly the screencast corpus the `screencast` keyframe detector and
the OCR leg were designed for. It also has stretches of pure motion graphics,
so the frame leg has something to be right *about*.

**whisperX is deliberately absent.** The worker answers
`POST /v1/audio/transcriptions` with `503 backend_unavailable` ("whisperx is
not installed"), and the documented `prefer_whisperx` fallback takes over. That
is the zero-GPU path from `mcp/README.md`, and it worked end to end without a
single code change:

```
worker: job failed task=stt label=5C_HPTJg5ek.opus: whisperx is not installed
mcp:    worker asked us to wait 10.0s (attempt 1) …
job_events: transcript from yt_auto (74 cues, model_key=youtube-asr-en-orig)
job_events: [warn] transcript came from yt_auto, not whisperX
```

The rest of the worker ran for real: **Qwen3-Embedding-0.6B** (1024-d) and
**SigLIP 2 so400m NaFlex** (1152-d, both towers) on CPU torch, **RapidOCR** on
onnxruntime.

### Environment deviations from `deploy/.env.example`

Three, all recorded in the harness, none hiding a failure:

1. **A separate CPU venv for the worker** (`~/.cache/vidtheque-smoke/worker-venv`),
   installed with `uv pip install --torch-backend=cpu ./worker sentence-transformers
   transformers==4.57.6 rapidocr==3.9.2 onnxruntime==1.28.0 …` — i.e. the `gpu`
   extra minus whisperX, with CPU torch wheels. `uv sync --extra gpu` would pull
   CUDA wheels for a machine with no CUDA.
2. **`IDLE_UNLOAD_SECONDS=20`** (default 300). This box has ~5 GB of free RAM;
   Qwen3 (2.4 GB fp32) and SigLIP 2 (4.3 GB fp32) resident together is an OOM.
   With a 20 s idle TTL the lifecycle manager unloads the text embedder while
   keyframes are being cut, and the frame embedder loads into the space. This
   is the lifecycle manager doing precisely its job on a resource it was not
   written for (RAM instead of VRAM).
3. **`VIDTHEQUE_WORKER_RETRIES=1`, `RETRY_MAX_WAIT_S=10`, `WORKER_TIMEOUT_S=600`**
   — the whisperX 503 is permanent here, so the default 3 retries only buy wall
   clock; and CPU embedding of a batch can exceed the 120 s default.

Plus one **workaround for a real bug** — the harness rewrites three `config`
rows before boot. See §4.1.

## 4. What did not work

Six findings. Nothing here was worked around in `mcp/` or `worker/` source —
1 is worked around **in the harness** (a data fix, loudly logged), the rest are
reported as-is.

### 4.1 — `config` model ids and `.env.example` model ids disagree, and the mismatch silently disables every vector leg  ⚠ blocker for a default install

- **Where**: `mcp/src/vidtheque_mcp/db/migrations/0001_initial.sql:31-39`
  (`text_embed.model = 'qwen3-embedding-0.6b'`,
  `frame_embed.model = 'siglip2-so400m-patch16-naflex'`,
  `ocr.model = 'rapidocr-v2'`) versus `deploy/.env.example:44,49,50`
  (`EMBED_MODEL=Qwen/Qwen3-Embedding-0.6B`,
  `IMAGE_EMBED_MODEL=google/siglip2-so400m-patch16-naflex`,
  `OCR_MODEL=rapidocr-default`).
- **What happens**: the worker reports the id it serves (`Embeddings.model` =
  `settings.embed_model`), and both sides compare it to the `config` string:
  - `pipeline/runner.py:840` (`_dimension_mismatch`) →
    `"the worker is serving 'Qwen/Qwen3-Embedding-0.6B' but the corpus is
    embedded with 'qwen3-embedding-0.6b'"` → `text_embed` is **skipped**;
    same for `frame_embed`.
  - `db/database.py:203-208` (`note_worker_drift`) → at query time this
    **disables the vector legs for the whole process**.
  So with the shipped defaults you get: no chunk vectors, no frame vectors,
  FTS-only search, and a `note:` blaming a model mismatch that the repo itself
  created.
- **Repro**: boot both services with `deploy/.env.example` values, index
  anything, watch `video_stages` — `text_embed`/`frame_embed` land `skipped`
  with that message.
- **Suggested fix**: make the migration seed exactly the identifiers
  `.env.example` ships (they are the drift check's whole subject), or normalise
  the comparison in one place (casefold + strip the `org/` prefix) — but the
  seed is the honest fix, because `model_key` in `video_stages` is meant to
  read back as the model that produced the row.
- **Harness workaround**: `scripts/e2e_smoke.py::align_config()` rewrites the
  three rows before first boot and prints what it changed. Turn it off with
  `--no-align-config` to see the bug.

Note `stt.model` (`'whisperx-large-v3'` vs the worker's `large-v3`) has the same
shape but is harmless: the STT path never compares names, and the worker logs
`ignoring requested model=whisperx-large-v3; worker serves large-v3`.

### 4.2 — OCR search hits carry an unusable `frame_id` (internal row id, not the public one)

- **Where**: `mcp/src/vidtheque_mcp/tools/search.py:333` —
  `frame_id=f"{row['video_id']}-{int(row['ord']):05d}"`, where `row['video_id']`
  comes from `_OCR_SQL` as `o.video_id`, i.e. the **integer `videos.id`**. The
  frame leg gets this right (`db/queries.py:479`:
  `v.public_id || '-' || printf('%05d', k.ord)`).
- **What happens**: OCR hits print and return `frame_id: "1-00033"` instead of
  `"5C_HPTJg5ek-00033"`. `tool-surface.md:100` defines `frame_id` as
  `<video_id>-<NNNNN>`, and `vidtheque://guide` tells the model to use only ids
  that appeared in a result — so the model does, and:

  ```
  get-frames frame_ids=["1-00033"]
    Frames: 0/1
    failed: 1-00033: video 1 is not in the corpus
  ```
- **Repro**: `search q="Cargo.toml" content_type=ocr` on this corpus, then feed
  the `frame_id` it returns to `get-frames`. Verified against the run's DB.
- **Suggested fix**: one line — build the id from the public id. Either select
  `v.public_id` in `_OCR_SQL` (join `videos`), or set `frame_id` after
  `_video_meta()` has filled `hit.public_id` (that loop already runs at
  `search.py:216-223`).

### 4.3 — SigLIP 2 backend breaks on transformers 5.x (both towers, 500)

- **Where**: `worker/src/vidtheque_worker/backends/siglip2_image_embed.py:148`
  and `:185` — `features = self._model.get_image_features(**inputs)` /
  `get_text_features(**inputs)` then `features.norm(...)`.
- **What happens**: on **transformers 5.14.1** those methods return a
  `BaseModelOutputWithPooling`, not a tensor:

  ```
  AttributeError: 'BaseModelOutputWithPooling' object has no attribute 'norm'
  POST /v1/embeddings/image        → 500   (frame_embed stage fails)
  POST /v1/embeddings/frame-query  → 500   (frame search leg skipped)
  ```

  The MCP side degraded correctly and said so — the frame stage soft-failed
  (`data_status: no_frames`) and search printed
  `note: … this worker serves no text->frame-space endpoint
  (/v1/embeddings/frame-query: 500 Internal Server Error) — the frame leg was
  skipped for this search.` A sibling *path* is what made this visible.
- **Scope**: `uv.lock` resolves **transformers 4.57.6** (whisperX pins
  `huggingface-hub<1.0`), and everything works there — this is a **latent**
  break, not a break of the locked install. It matters because
  `DECISIONS.md` and `deploy/.env.example` both say the intended target is
  transformers ≥5.14 (for the processor's automatic lowercase + pad-to-64), so
  the day the whisperX pin frees, the frame legs die.
- **Repro**: `pip install transformers==5.14.1` into the worker env, `POST
  /v1/embeddings/frame-query {"input":"a terminal"}` → 500.
- **Suggested fix**: unwrap defensively in `_encode`/`_encode_text`, e.g.
  `features = getattr(out, "pooler_output", out)` — or, since 5.x's
  `get_*_features` returns the full output object, take the documented tensor
  attribute and keep the 4.x path working. Worth a test that fakes both return
  shapes (no download needed).
- **Harness**: `scripts/e2e_smoke.py` pins `transformers==4.57.6` to match
  `uv.lock`, with a comment naming this bug.

### 4.4 — the OCR leg's SQL prefilter drops OCR hits the contract says to keep

- **Where**: `mcp/src/vidtheque_mcp/db/queries.py:403-408`, the `NOT EXISTS`
  clause in `_OCR_SQL`.
- **What happens**: an OCR line is dropped whenever *any* transcript cue
  matching the same query overlaps its timestamp ±5 s **and is longer** — with
  **no text-similarity test at all**. `tool-surface.md:296-303` requires
  containment or ≥0.8 trigram Jaccard, and requires the two to *collapse into
  one result* tagged `[transcript+ocr]`, not to vanish. That correct rule *is*
  implemented, in Python (`tools/search.py:387-424`) — but the SQL prefilter is
  strictly more aggressive than the Python rule, so the Python half never sees
  the rows.
- **Consequence**: on a screencast where the presenter says what is on screen —
  the corpus this product is for — searching the OCR channel for a narrated
  word returns nothing, **with no `note:`**, which is the "`all` means all /
  never silently narrows" invariant broken in the quietest possible way. With
  `content_type=ocr` there is not even a transcript hit on screen to explain it.

  ```
  search q="cargo" content_type=ocr   → Results: 0/0 · Legs: … ocr 0    (no note)
  ```
  Both surviving OCR candidates were suppressed by transcript cues:
  `90.8s "± Install Cargo"` and `96.8s "rust-demo $ cargo new rusty_app"` —
  the second is a shell command, not a restatement of the narration.
  `search q="Cargo.toml" content_type=ocr` → 3 hits, because the phrase is
  never spoken.
- **Repro**: the two searches above on this corpus; or run `_OCR_SQL` with and
  without the `NOT EXISTS` clause (the harness's sibling `ocr_echo` search
  bakes the demonstration in).
- **Suggested fix**: either delete the prefilter and let the Python dedup own
  the rule, or make it a conservative superset —
  `AND instr(lower(t.text), lower(o.text)) > 0` (cheap containment, matches the
  Python test's first branch) — and skip it entirely when the transcript leg is
  not running.

### 4.5 — `get-frames` claims URLs are signed when they are not, and prints `None`

- **Where**: `mcp/src/vidtheque_mcp/tools/frames.py:140-141, 167-171`.
- **What happens**: in `none` mode `_signed_url()` returns `expires_at = 0`;
  `expiry_note` is then `0`, which is `is not None`, so the footer prints with
  `iso_z(0) → None`:

  ```
  URLs expire None. They are signed — no auth header needed to fetch them.
  ```

  Both halves are wrong there: nothing expires, and nothing is signed (by
  design — the docstring at `:183` says an unsigned path is honest in `none`
  mode). In `token` mode the same line is correct
  (`URLs expire 2026-08-09T18:27:39Z.`).
- **Suggested fix**: `if expiry_note:` instead of `if expiry_note is not None:`.

### 4.6 — two cosmetic reporting bugs

- **`vidtheque://context` reports `total_duration_seconds: 0`** for a 149 s
  corpus. `tools/resources.py:143` derives seconds from the rollup's `hours`,
  which `db/queries.py:663` computes as `ROUND(SUM(duration_s)/3600.0, 1)` — so
  anything under ~3 minutes rounds to `0.0 h` and then to 0 seconds. Sum the
  seconds and derive hours for display, not the other way round.
- **`list-videos` says "missing channels"** when it means missing *coverage
  channels* (`tools/library.py:146`): with only the transcript indexed it
  printed `1 video(s) have missing channels`, which reads as a missing YouTube
  channel name — and `channel` is a filter parameter elsewhere in the same
  tool. Suggest "1 video(s) have incomplete coverage".

### Not a bug, worth knowing

- `sentence-transformers` 5.7.0 emits
  `FutureWarning: get_sentence_embedding_dimension has been renamed to
  get_embedding_dimension` from `qwen3_embed.py:83`. Harmless today; it is a
  rename, not a removal.
- The worker logs `VRAM accounting disabled (pynvml/nvidia-ml-py not
  installed); loads will not be gated` and proceeds — exactly the documented
  degradation for a machine with no NVML.
- `keyframes.dup_of` was `NULL` for all 44 frames: at a 24/256-bit Hamming
  threshold, nothing in this fast-cut screencast is a near-duplicate. The dedup
  path is therefore **untested** by this run; a slide deck with a static
  chrome would exercise it.

## 5. The harness

`scripts/e2e_smoke.py` — one file, no test-suite coupling.

```bash
uv run python scripts/e2e_smoke.py                       # the default video
uv run python scripts/e2e_smoke.py --url https://youtu.be/<id>
uv run python scripts/e2e_smoke.py --channels transcript,ocr   # skip SigLIP
uv run python scripts/e2e_smoke.py --no-align-config           # see bug 4.1
```

- Creates the CPU worker venv on first run (`uv pip install --torch-backend=cpu`).
- Fresh data dir per run (`scripts/.smoke-data/run-<ts>/`, gitignored), so no
  two runs share a database; `--keep` is a no-op reminder, `--data-dir` pins it.
- Boots both services with **scrubbed** environments (any inherited
  `VIDTHEQUE_*` / `WORKER_URL` / `DEVICE` is dropped) so a run is reproducible
  from a dirty shell.
- Drives the real MCP client, prints every call and its output, then writes
  `smoke-report.json` with the calls, the timings, `video_stages`,
  `job_events`, row counts and byte sizes.
- Exits non-zero if the job did not reach `done`.

Three consecutive full runs were made after the transformers pin, all green and
within ±1 s of each other on every compute stage (`fetch` varied 34–41 s with
the network). Row counts were byte-identical across runs: 74 cues, 5 chunks,
44 keyframes, 419 OCR lines, 44 frame vectors.

## 6. Verdict

**The loop is real, and the parts that are hard to fake are the ones that
worked.** A single `index-video` call built a 2.6 MB index with 74 word-timed
cues, 5 embedded chunks, 44 keyframes, 419 OCR lines and 44 frame vectors in
140 s of pure CPU, and all three retrieval legs then answered correctly with
deep links that land on the right second. The zero-GPU fallback is not a
paragraph in a README — it is a 503 the pipeline catches, a caption track it
prefers, a `model_key` that records the downgrade, and a `warn` event that says
so. Per-stage failure is real (§4.3's soft-failed frame stage left the video
searchable and `data_status` said `no_frames`). The capability URL is real. The
error contract is real.

What is not yet real is a **default install**: with the values this repo ships
in `deploy/.env.example` and `0001_initial.sql`, both vector legs turn
themselves off on the first request (§4.1). That is one migration edit away
from fixed, and it is the single highest-value change on this list. After it,
§4.2 (one line) and §4.4 (one clause) are what stand between the OCR channel
and being trustworthy.
